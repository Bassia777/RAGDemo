# Wiki RAG 本地学习 MVP 设计

日期：2026-07-31
状态：设计已确认，待用户审阅书面规格

## 1. 目标

在一台 16GB Apple Silicon Mac 上搭建一个完全本地运行、可逐层观察的 Wiki RAG 最小系统。系统只抓取用户明确指定的 10～20 篇内部 Wiki 页面，通过本地关键词检索、向量检索和 Ollama 生成带引用的答案。

本项目以理解 RAG 完整流程为第一目标，不优先使用 AnythingLLM、Open WebUI、LangChain 或 LlamaIndex 等高级封装。透明实现跑通后，再尝试可视化或框架化方案。

## 2. 已知约束

- Wiki 使用公司 SSO；
- 登录后页面正文直接包含在静态 HTML 中；
- 暂时没有 Wiki 机器人账号；
- 学习阶段临时使用个人账号的浏览器登录状态；
- 不向程序提供或保存个人账号密码；
- 只抓取手工列出的 10～20 个 URL；
- 所有 Wiki 内容、索引和模型推理均保留在本机；
- Mac 为 Apple Silicon、16GB 内存；
- 第一版使用命令行，不开发 Web 界面。

## 3. 范围

### 3.1 包含

- Playwright 启动浏览器，由用户手动完成 SSO 登录；
- 将浏览器会话保存为本地敏感文件；
- 读取 URL 白名单并抓取指定页面；
- 保存原始 HTML 和页面元数据；
- 提取标题、章节、正文、列表、表格和代码块；
- 按章节进行语义分块；
- 建立 BM25 关键词索引；
- 使用本地 Embedding 建立 FAISS 向量索引；
- 使用 RRF 融合两路检索结果；
- 调用 Ollama 本地模型生成答案；
- 返回原文引用、页面标题、章节和 Wiki 链接；
- 保存中间结果，支持逐层检查和离线测试。

### 3.2 不包含

- 自动遍历整个 Wiki；
- 抓取未列入白名单的页面；
- 每日定时同步和复杂增量更新；
- OpenSearch、PostgreSQL 或服务器部署；
- Reranker；
- 页面级权限过滤；
- 多用户和多租户；
- Web 聊天界面；
- Agent 工作流；
- 外部大模型 API；
- 生产环境安全与高可用设计。

## 4. 系统流程

```text
urls.txt
   │
   ▼
Playwright 浏览器 ── 用户手动完成 SSO
   │
   ├── 保存本地会话状态
   └── 抓取白名单中的 10～20 个页面
                     │
                     ▼
             原始 HTML 与元数据
                     │
                     ▼
              HTML 解析与清洗
                     │
                     ▼
              按标题和章节分块
                ┌────┴────┐
                ▼         ▼
              BM25      Embedding
                          │
                        FAISS
                └────┬────┘
                     ▼
                  RRF 融合
                     │
                     ▼
              Top-K 证据片段
                     │
                     ▼
                Ollama 本地模型
                     │
                     ▼
           答案＋原文片段＋Wiki 链接
```

## 5. 模块边界

### 5.1 登录模块

职责：启动可见浏览器，让用户手动完成 SSO，并保存浏览器会话状态。

安全要求：

- 不读取或保存账号密码；
- 会话文件只保存在本机；
- 会话文件加入 `.gitignore`；
- 日志不得输出 Cookie、Token 或请求认证头；
- 会话过期后由用户重新登录；
- 不尝试绕过 SSO、验证码或公司安全策略。

### 5.2 抓取模块

职责：读取 `urls.txt`，验证 URL 是否属于配置的 Wiki 域名和路径，然后使用已登录的浏览器上下文访问页面。

约束：

- 仅访问 URL 白名单；
- 单线程或极低并发；
- 请求之间保留 1～2 秒间隔；
- 设置页面加载超时；
- 失败页面记录原因，不无限重试；
- 不自动点击或发现其他页面链接；
- 不提交表单，不修改 Wiki 内容。

每篇页面保存：

```text
page_id
url
title
fetched_at
http_or_page_status
raw_html_path
content_hash
```

### 5.3 解析模块

职责：从原始 HTML 中提取知识正文，并保存可读的结构化结果。

保留：

- 页面标题；
- H1～H6 章节路径；
- 正文段落；
- 有序和无序列表；
- 代码块与命令；
- 表格及其表头；
- 原始页面 URL。

删除：

- 顶部导航和侧边栏；
- 页脚、编辑按钮和搜索组件；
- 脚本、样式和隐藏元素；
- 重复菜单和无关模板文字。

解析后的每个页面保存为 JSON，便于直接阅读和排错。

### 5.4 分块模块

职责：根据页面标题和章节层级切分文档。

第一版规则：

- 优先按标题和自然段切分；
- 目标长度约 300～800 个中文字符；
- 超长章节继续按段落拆分；
- 太短章节与相邻正文合并；
- 代码块尽量保持完整；
- 表格与表头保持在同一分块；
- 每个分块保留页面标题、章节路径、URL 和分块序号。

分块结果保存为 JSONL，用户可以直接查看每一块的内容。

### 5.5 关键词检索模块

职责：使用 BM25 对问题和分块进行关键词匹配。

需要保留错误码、接口名、配置项、类名、版本号、英文大小写、下划线和代码符号。模块单独输出 Top-K 分块、分数和排名，使关键词检索效果可观察。

### 5.6 向量检索模块

职责：使用支持中文的本地 Embedding 模型将分块转换为向量，并保存到 FAISS。

Embedding 文本由页面标题、章节路径和正文组成。模型名称、向量维度、分块哈希和索引版本需要写入索引元数据，防止模型变化后错误复用旧索引。

模块单独输出向量检索的 Top-K 分块、相似度和排名。

具体 Embedding 型号在实施计划阶段根据 Ollama、Sentence Transformers 的可用性和 16GB 内存约束确定，必须支持中文并可完全本地运行。

### 5.7 融合模块

职责：使用 Reciprocal Rank Fusion 合并 BM25 和向量检索排名。

第一版不手工调节不同检索器的原始分数权重。融合结果去重后选择约 5 个证据片段，并输出每个结果分别来自哪一路检索及原始排名。

### 5.8 答案生成模块

职责：把问题和 Top-K 证据发送给 Ollama 本地模型，生成简洁答案。

生成约束：

- 只能依据提供的证据回答；
- 每个关键结论标记证据编号；
- 证据不足时明确说明未找到可靠资料；
- 不得编造页面名称、URL、参数或步骤；
- 最终链接由程序根据证据元数据生成；
- 模型失败时仍返回检索片段和链接。

生成模型优先选择适合 16GB Apple Silicon 的 3B～4B 量化模型。具体型号保持配置化，在实施阶段通过小型测试确定。

### 5.9 命令行模块

第一版命令行支持以下独立动作：

```text
登录并保存会话
抓取白名单页面
解析原始 HTML
生成分块
建立或重建索引
仅运行 BM25 查询
仅运行向量查询
运行融合查询
运行完整问答
执行测试问题集
```

这些动作必须能够分别运行，避免把整个系统封装成一个无法观察的黑盒。

## 7. 可观察性与学习检查点

每一步都生成可检查产物：

1. 抓取后检查原始 HTML 是否包含正文；
2. 解析后比较原始页面和结构化 JSON；
3. 分块后逐条检查章节路径、代码块和长度；
4. 对同一个问题分别查看 BM25 与向量 Top-K；
5. 查看 RRF 如何改变排名；
6. 查看最终传给 Ollama 的完整证据；
7. 对照引用判断答案是否被证据支持。

日志只记录页面 ID、URL、阶段、耗时、状态和错误，不记录 Cookie、Token 或完整请求头。

## 8. 测试与验收

### 8.1 测试数据

为 10～20 篇页面准备 10～20 道问题，包括：

- 页面中有直接答案的问题；
- 同义表达问题；
- 错误码、接口名和配置项精确查询；
- 需要两个片段共同回答的问题；
- 当前页面集合中不存在答案的问题。

每道题标注正确页面、正确章节和答案要点。

### 8.2 MVP 验收标准

- 能通过手动 SSO 建立可复用的本地会话；
- 只抓取白名单中的 10～20 个页面；
- 标题、正文、章节和代码块解析基本正确；
- 每个中间阶段均有可人工阅读的产物；
- 大多数有答案问题的正确页面进入融合结果 Top 5；
- 答案引用链接真实且来自检索证据；
- 无答案问题能够拒答或只返回相关页面；
- Wiki 内容、索引和模型请求不离开本机；
- 删除本地会话文件后，程序无法继续访问受保护页面。

## 9. 实施顺序

后续实施计划按照以下顺序展开：

1. 建立项目骨架、配置与敏感文件规则；
2. 完成 Playwright 手动 SSO 和会话保存；
3. 抓取一个测试页面并保存原始 HTML；
4. 扩展到 URL 白名单；
5. 完成 HTML 解析和结构化输出；
6. 完成章节分块；
7. 完成 BM25 检索；
8. 完成本地 Embedding 与 FAISS；
9. 完成 RRF 融合；
10. 接入 Ollama 并实现带引用答案；
11. 建立问题集并逐层评测；
12. 编写本地使用说明和安全注意事项。

## 10. 后续升级方向

本地透明版本跑通并理解后，可以依次尝试：

1. 使用 AnythingLLM 或 Open WebUI 复现同一批文档；
2. 比较封装工具和透明实现的分块、召回与引用差异；
3. 引入 Reranker；
4. 增加每日增量更新；
5. 扩大到更多 Wiki 页面；
6. 获得机器人账号并替换个人浏览器会话；
7. 评估 OpenSearch 和服务化部署。

## 11. 设计结论

第一阶段选择透明的 Python 本地实现。Playwright 仅处理手动 SSO 和小规模页面访问；BeautifulSoup 负责解析；BM25 与本地 Embedding/FAISS 分别提供关键词和语义检索；RRF 合并排名；Ollama 基于约 5 个证据片段生成带引用答案。

该方案刻意保留每个中间步骤和结果，使学习者能定位抓取、解析、分块、召回、融合或生成中的具体问题。完成理解后，再使用可视化和高级框架封装同一流程。
