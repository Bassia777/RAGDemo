# 企业内部 Wiki RAG 检索机器人试点设计

日期：2026-07-31
状态：设计已确认，待实施计划评审

## 1. 背景与目标

公司内部 Wiki 约有数百 GB 内容，主要由文字版技术实现、技术指南、故障排查和接入说明组成。当前 Wiki 没有可用的官方 API，只能在登录后通过静态 HTML 页面读取正文。所有内部员工均可访问试点内容，因此第一阶段不需要实现页面级用户权限过滤。

本项目首先选择一个高频技术领域或 Wiki 空间进行试点，覆盖约 1,000～10,000 篇页面。系统接收用户问题后，应返回简洁答案、引用的原文片段和可点击的 Wiki 链接；证据不足时必须明确拒答或仅推荐相关资料。

试点采用每日增量同步。由于内部资料能否发送给外部模型尚未确定，Embedding、重排序和生成模型必须通过统一接口封装，支持外部服务和内网模型互换。

## 2. 范围

### 2.1 试点范围

- 一个技术领域或 Wiki 空间；
- 约 1,000～10,000 篇静态 HTML 页面；
- 登录态页面采集、清洗、分块和每日增量更新；
- BM25 与向量相结合的混合检索；
- 候选片段重排序；
- 基于证据的答案生成；
- 原文片段、页面标题、章节和 Wiki 链接引用；
- 无答案拒答、组件降级、日志和离线评测；
- 小范围用户试用与反馈闭环。

### 2.2 暂不包含

- 全量数百 GB Wiki 一次性接入；
- 页面级或用户级权限隔离；
- 接近实时的内容同步；
- 自动修改 Wiki 内容；
- 无人工审核的全公司推广；
- 依赖某个固定厂商的模型或向量数据库接口。

## 3. 总体架构

```text
                    每日同步
                       │
Wiki → 登录态爬虫 → 原始页面存储
                       │
                 解析、清洗、去重
                       │
              按标题和章节进行分块
                  ┌────┴────┐
                  │         │
             关键词索引   向量索引
                  └────┬────┘
                       │
用户问题 → 查询处理 → 混合检索 → 重排序
                                   │
                           选择可靠证据
                                   │
                         大模型生成简洁答案
                                   │
                      答案＋原文片段＋Wiki链接
```

建议试点阶段尽量减少组件数量：

- 原始 HTML：对象存储或文件存储；
- 页面状态与采集元数据：PostgreSQL；
- 关键词和向量索引：优先统一使用 OpenSearch；
- Embedding、Reranker 和生成模型：统一接口封装；
- 同步调度：每日定时任务；
- 运行观测：结构化日志、指标和失败任务队列。

## 4. 数据采集与增量同步

### 4.1 页面发现

爬虫从试点空间入口页开始，递归提取站内链接。URL 必须规范化、去重，并限制在明确的试点域名和路径范围内。

需要排除：

- 登录、编辑、历史版本等功能页；
- 搜索结果、分页参数和 URL 锚点产生的重复页面；
- 用户主页、评论区和无业务价值的导航页；
- 非试点空间页面；
- 脚本、样式等非知识内容。

首轮抓取完成后保存页面清单，作为每日增量同步的基线。

### 4.2 身份认证与运行安全

使用专用 Wiki 机器人账号，不使用个人账号。登录凭证或 Cookie 通过安全配置注入，不写入代码仓库。采集器需要具备：

- Cookie 到期检测和告警；
- 请求并发与频率限制；
- HTTP 429、5xx 和网络故障重试；
- 指数退避；
- 单页大小和下载超时限制；
- 采集审计日志；
- Wiki 管理方明确授权。

试点初期建议并发数为 5～10，并根据 Wiki 服务负载逐步调整。

### 4.3 原始数据保存

所有页面先保存原始 HTML，再解析正文，以便后续调整解析器、分块或索引策略时离线重建。

页面记录至少包含：

```text
page_id
canonical_url
title
raw_html_location
content_hash
first_seen_at
last_seen_at
last_crawled_at
http_status
parser_version
document_status
```

### 4.4 正文解析与清洗

保留页面标题、H1～H6 标题层级、正文段落、代码块、表格、列表、图片说明、更新时间和原始链接。删除顶部导航、侧边栏、页脚、编辑按钮、重复菜单和无关模板文本。

代码块、命令、配置项、接口名和错误信息必须保持原始格式，不能按普通自然语言过度清洗。

### 4.5 每日增量同步

每日读取页面清单，抓取页面并对规范化正文计算内容哈希：

- 哈希不变：更新检查时间，不重新生成向量；
- 内容变化：重新解析、分块并更新索引；
- 新页面：新增页面和索引；
- 暂时访问失败：保留旧索引，进入重试队列；
- 连续多次返回 404：标记删除并移出在线索引；
- URL 变化：尽可能通过稳定页面 ID 判断移动或重命名。

## 5. 文档分块

分块优先遵循页面标题结构，不采用单纯固定字符数切割。

建议规则：

- 每块约 300～800 个中文字符；
- 超长章节按自然段继续拆分；
- 相邻块保留少量语义重叠；
- 每块携带页面标题和完整章节路径；
- 代码块尽量保持完整；
- 表格必须与表头共同保存；
- 太短章节与相邻内容合并；
- 空页面、纯导航页和纯链接目录不生成普通正文块。

每个分块至少保存：

```text
chunk_id
page_id
page_title
section_path
content
canonical_url
updated_at
document_version
chunk_index
previous_chunk_id
next_chunk_id
content_hash
```

用于生成 Embedding 的内容同时包含页面标题、章节路径和正文，防止片段脱离主题上下文。

## 6. 查询、混合检索与重排序

### 6.1 查询处理

查询处理需要保留错误码、类名、接口名、配置项、版本号、下划线、大小写和代码符号。系统可以额外生成语义化查询，但不能覆盖原始技术关键词。

例如：

```text
原问题：有人遇到 ERR_CONN_102 吗？SDK 一直超时怎么处理？
关键词查询：ERR_CONN_102 SDK 超时
语义查询：SDK 连接超时时应该如何排查和处理？
```

### 6.2 混合召回

系统并行执行：

- BM25 关键词检索，召回约 30～50 个候选；
- 向量语义检索，召回约 30～50 个候选。

两路结果使用 RRF 融合、去重。关键词检索负责错误码、API、配置项和精确名称；向量检索负责同义表达、概念问题、故障现象和操作意图。

### 6.3 元数据过滤

索引支持按技术领域、文档状态、语言、产品版本、更新时间和文档类型过滤。旧版本文档不能仅因时间较早而默认删除，应在排序和答案中明确版本差异。

### 6.4 重排序

融合后的约 50～80 个候选交给 Reranker，最终保留 5～10 个最相关片段。没有可用 Reranker 时，使用融合排名降级。

命中片段存在语义截断时，可以补充相邻分块用于生成，但不能无条件扩展所有候选。

### 6.5 无可靠结果

当检索结果未达到相关性标准时，系统不允许模型依靠自身记忆回答。机器人应明确说明当前试点 Wiki 中没有可靠资料，并可返回最接近的页面供用户自行判断。

## 7. 答案生成与引用

### 7.1 模型职责

生成模型只负责阅读证据、归纳答案、合并一致信息、指出冲突并标注引用。系统提示明确要求：

- 只能依据提供的 Wiki 资料回答；
- 资料不足时必须说明无法确定；
- 不得编造接口、参数、步骤、链接或引用；
- 文档存在版本冲突时分别列出；
- 每个关键结论必须附证据编号。

### 7.2 证据格式与引用

检索结果以编号资料块提供给模型，每块包含页面、章节、更新时间、链接和正文。模型只输出资料编号，最终 Wiki 链接由应用程序根据编号渲染，从而避免生成虚假 URL。

推荐回答结构：

```text
简要结论

具体步骤
1. …… [资料1]
2. …… [资料2]

注意事项
- 版本限制…… [资料3]

参考资料
- 《页面标题》— 章节名称
```

### 7.3 证据检查

生成答案前检查：

- 是否至少存在一个超过阈值的证据；
- 证据是否直接支持问题；
- 是否存在版本冲突；
- 是否命中过期或废弃标记；
- 是否只是主题相似而没有直接答案。

### 7.4 提示注入防护

Wiki 内容作为不可信引用资料处理：

- 文档内容不能覆盖系统指令；
- 清理脚本、隐藏 HTML 和不可见文字；
- 限制单页面占用的上下文比例；
- 回答模型不具备数据库写入或爬虫管理权限；
- 忽略文档中要求模型改变行为的指令。

### 7.5 多轮对话

系统利用有限的对话历史补全当前问题，但每轮仍需重新检索。仅保留近期对话摘要，避免长期历史污染查询。

## 8. 模型抽象与降级

模型能力通过统一接口封装：

```text
embed(texts) → vectors
rerank(query, documents) → scores
generate(question, evidence) → answer
```

模型安全审批完成前，可以先完成采集、关键词检索、向量检索和离线评测。审批后根据规定接入外部托管模型或内网模型。

运行降级规则：

- 生成模型失败：返回排序后的原文片段和链接；
- Reranker 失败：使用 RRF 融合排名；
- 向量服务失败：退回 BM25 关键词检索；
- 单页面采集失败：保留上一版本索引并重试；
- 每次回答记录使用的 `chunk_id`、模型和索引版本。

## 9. 评测体系

### 9.1 评测集

从聊天记录、高频咨询、新员工问题、故障记录、搜索词和技术支持工单中收集 100～300 个真实问题。每道题标注：

```text
问题
标准答案要点
正确页面
正确章节
不可接受的错误
适用版本
问题类型
```

评测集覆盖精确查找、操作指南、故障排查、概念解释、多文档综合、无答案问题和版本冲突。

### 9.2 分层指标

| 层级 | 指标 | 目标 |
|---|---|---|
| 数据采集 | 页面覆盖率、解析成功率 | 资料是否进入系统 |
| 检索召回 | Recall@5、Recall@10 | 正确章节是否被找到 |
| 重排序 | MRR、NDCG、Top-5 命中率 | 正确证据是否位于前列 |
| 答案生成 | 正确性、完整性、忠实性 | 是否依据证据回答 |
| 引用 | 引用正确率、链接有效率 | 是否可追溯 |
| 系统 | 延迟、失败率、成本 | 是否可稳定使用 |

建议试点上线门槛：

- 抓取和解析成功率不低于 95%；
- 正确章节进入 Top 5 的比例不低于 85%；
- 引用链接有效率接近 100%；
- 明显幻觉率低于 2%；
- 无资料问题能够稳定拒答；
- P95 响应时间控制在 10 秒以内，或由团队确认其他可接受标准。

### 9.3 人工评分与错误分类

领域专家按 0～3 分评价答案：0 分为错误或无关，1 分为部分相关但不能解决问题，2 分为基本正确但缺少重要信息，3 分为正确、完整且引用可靠。

失败案例分类为采集缺失、解析错误、分块错误、关键词召回失败、向量召回失败、重排序失败、证据充分但生成错误、引用错误或源文档过期。调优必须基于错误类别，而不是盲目更换模型。

### 9.4 用户反馈

回答页面提供“有帮助”“没有帮助”“引用不正确”“内容已过期”“未找到所需内容”等反馈。负反馈保存问题、候选片段、最终证据、答案、系统版本和反馈原因，并经人工检查后加入评测集。

## 10. 分阶段交付

### 阶段一：数据可用性验证

- 确定试点空间和授权；
- 抓取 1,000～10,000 篇页面；
- 保存原始 HTML；
- 完成清洗、去重和每日同步；
- 抽样检查正文、代码块和表格。

### 阶段二：检索验证

- 建立 BM25 与向量索引；
- 实现 RRF 融合与重排序；
- 建立首批真实评测集；
- 比较 Wiki 原搜索、BM25、纯向量和混合检索；
- 在不依赖生成模型的情况下证明检索价值。

### 阶段三：问答机器人

- 接入获批的模型；
- 生成带引用答案；
- 实现拒答、冲突提示和降级；
- 支持有限多轮对话；
- 记录完整检索与生成链路。

### 阶段四：小范围试用

- 邀请约 20～50 名目标用户；
- 运行两到四周；
- 每周分析失败案例并扩充评测集；
- 调整解析、分块、检索和答案策略。

### 阶段五：逐步扩容

试点达标后逐个增加 Wiki 空间。每次扩容重新检查数据量、索引容量、同步耗时、领域术语、文档质量和检索指标，不直接从试点跳到数百 GB 全量索引。

## 11. 关键风险

| 风险 | 应对措施 |
|---|---|
| Wiki 页面结构变化导致解析失败 | 解析器版本化、抽样检测、解析成功率告警 |
| 抓取影响 Wiki 服务 | 限速、低并发、退避、与管理员协商窗口 |
| Cookie 到期 | 专用账号、到期检测、告警和安全更新机制 |
| 文档重复、过期或互相冲突 | 内容哈希去重、版本元数据、冲突提示 |
| 技术术语被查询改写破坏 | 保留原始查询，关键词与语义查询并行 |
| 模型编造答案或链接 | 证据阈值、编号引用、程序生成链接、可靠拒答 |
| 外部模型审批未完成 | 模型接口抽象，优先完成数据和检索阶段 |
| 离线指标好但用户体验差 | 小范围试用、真实反馈和持续错误分析 |

## 12. 学习路径

建议按照以下顺序学习并与试点同步实践：

1. 倒排索引、BM25、Recall、Precision 和 MRR；
2. Embedding、相似度和向量索引；
3. HTML 解析、文本清洗与语义分块；
4. 混合检索与 RRF；
5. Cross-Encoder 重排序；
6. RAG 上下文组织、引用和可靠拒答；
7. 离线评测、人工评分与错误分析；
8. 增量索引、监控、成本和安全治理。

## 13. 设计结论

试点采用“登录态静态 HTML 每日增量抓取＋原始数据留存＋按章节分块＋OpenSearch 混合检索＋可替换重排序与生成模型＋答案引用和可靠拒答”的方案。

项目首先验证采集和检索质量，再接入生成模型；通过 100～300 个真实问题建立可量化评测，在一个技术领域达标后逐步扩容。该路径能够在模型安全策略尚未确定的情况下继续推进，并控制全量数百 GB 数据带来的成本与质量风险。
